# F-02 — Identidade global e seleção autorizada de oficina

## Fluxo de autenticação e autorização

1. O cliente envia email e senha por HTTP Basic. Em produção, o transporte deve
   usar HTTPS. Não há sessão nem oficina persistida no login.
2. `GlobalAuthenticationProvider` chama `GlobalAuthenticationService`.
   `find_auth_identity(email)` consulta a identidade global sem liberar SELECT em
   `users` ao runtime. O usuário precisa estar `ACTIVE` e a senha deve corresponder
   ao BCrypt armazenado. Novas senhas usam BCrypt com custo 12.
3. O principal do Spring Security contém apenas UUID e email; a senha é descartada.
4. `GET /api/oficinas/{tenantId}/selecao` chama a interface
   `AuthorizedTenantOperations`. A identidade vem do `SecurityContext`, nunca de
   parâmetros, headers de identidade ou do UUID da oficina enviado pelo cliente.
5. O executor abre uma transação `REQUIRES_NEW` e chama
   `authorize_tenant_membership(userId, tenantId)`. Usuário, oficina e vínculo
   precisam estar ativos. A função restaura o GUC anterior após a consulta.
6. Depois da autorização, o executor configura o ThreadLocal e
   `set_config('app.tenant_id', tenantId, true)`. JPA e JDBC compartilham a conexão
   e executam a operação dentro dessa transação.
7. Commit ou rollback encerram o GUC local. O escopo restaura o ThreadLocal
   anterior e o filtro HTTP o limpa no início e no fim da requisição.

Não há autenticação: `401`. Há identidade válida, mas não há autorização: `403`,
sem revelar se a oficina existe, está suspensa ou não possui vínculo. Um UUID
malformado retorna `400`. Métodos HTTP que alteram estado continuam sujeitos a CSRF.

Selecionar uma oficina não autoriza requisições futuras. Cada operação precisa
executar novamente pelo executor; consultas JPA não podem ser adiadas para depois
do callback, nem transferidas para outra thread. Regras ArchUnit impedem que a
camada HTTP use infraestrutura e que classes de produção contornem o executor
usando `TenantScope` ou alterando diretamente o contexto.

## RLS e privilégios

| Objeto ou capacidade | `fixflow_runtime` | `fixflow_migrator` |
| --- | --- | --- |
| `users` | Sem acesso direto | Proprietário; manutenção de identidades |
| `tenants`, `app_users` | SELECT sujeito a RLS | Proprietário, também sujeito a FORCE RLS |
| `tenant_memberships` | SELECT sujeito a RLS | Proprietário; policy de consulta por tenant |
| `find_auth_identity`, `authorize_tenant_membership` | EXECUTE | Proprietário das funções |
| `legacy_user_identity_migrations` | Sem acesso | Proprietário; trilha do backfill |
| `backfill_legacy_app_users` | Sem EXECUTE | Execução de manutenção como proprietário |
| SUPERUSER, CREATEROLE, CREATEDB, REPLICATION, BYPASSRLS | Não | Não exigidos pelo aplicativo |
| Propriedade de banco, schema público ou relações públicas | Não | Separada do runtime |
| CREATE em banco/schema público ou participação em outras roles | Não | Apenas manutenção controlada |

As funções SECURITY DEFINER usam `search_path` restrito e nomes de tabelas
qualificados; o privilégio EXECUTE é revogado de PUBLIC. O backfill é SECURITY
INVOKER e não pode elevar privilégios do runtime.

`ENABLE ROW LEVEL SECURITY` e `FORCE ROW LEVEL SECURITY` se aplicam às tabelas
de oficina. Sem contexto, as policies não permitem visualizar linhas de tenants.
Como o próprio runtime configura o GUC, o controle pressupõe SQL confiável na
aplicação: uma injeção SQL ou credencial de runtime comprometida pode configurar
outro tenant. Por isso são necessários SQL parametrizado, seleção via executor e
nenhuma API que exponha SQL arbitrário ou o contexto diretamente.

## Migração controlada do legado — V9

`app_users` continua preservada e legível por tenant. A V9 cria a trilha
`legacy_user_identity_migrations`, com o UUID de origem, identidade global,
oficina e indicadores de criação de identidade/vínculo e redefinição de senha.
Não há exclusão de dados legados nem liberação automática de acesso.

Regras do backfill:

- Email é comparado sem distinguir maiúsculas/minúsculas; espaços nas bordas e
  emails vazios bloqueiam a execução para revisão manual.
- Registros do mesmo email só são consolidados quando possuem o mesmo hash.
  Hashes BCrypt diferentes podem representar a mesma senha com salts diferentes;
  isso exige verificação de titularidade, não uma união automática.
- Conflitos com credenciais de uma identidade existente ou com UUID de outro
  usuário abortam a operação inteira.
- Identidades existentes e seus vínculos mantêm senha, status e role.
- Novas identidades ficam `SUSPENDED`; novos vínculos ficam `INVITED/VIEWER`.
  Nenhum OWNER ou ADMIN é inferido do legado.
- BCrypt válido é preservado. Hash inválido é substituído por
  `!RESET_REQUIRED!`, que não é uma senha utilizável; a origem permanece intacta.
- Registros já mapeados são ignorados. A função pode ser chamada novamente,
  inclusive na mesma transação, sem duplicar identidades ou vínculos.

A operação bloqueia as tabelas envolvidas durante o backfill e cria policies
transitórias exclusivamente para o migrator, removidas antes do retorno. Não há
policy temporária persistida nem privilégio adicional para o runtime. Falhas
revertem dados e DDL da chamada. Flyway executa a V9 atomicamente.

### Operação e recuperação

Antes de executar em outro ambiente, conferir origem, conflitos, quantidade de
linhas e snapshot de recuperação. Revisar a janela de manutenção devido aos locks.
Executar pelo fluxo normal do Flyway da aplicação, nunca rodar o arquivo SQL
manualmente fora do histórico do Flyway.

```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments="--server.port=0"
```

Interromper essa execução após a confirmação da migration e conferir o histórico
e a trilha usando a credencial do migrator:

```sql
SELECT version, success FROM public.flyway_schema_history WHERE version = '9';
SELECT count(*) AS migrated_records,
       count(DISTINCT user_id) FILTER (WHERE created_identity) AS created_identities,
       count(*) FILTER (WHERE requires_password_reset) AS reset_required
FROM public.legacy_user_identity_migrations;
```

Ativação posterior exige verificar titularidade, redefinir senhas marcadas e
aprovar explicitamente a role e o status de cada vínculo. A F-02 não implementa
o fluxo de recuperação de senha ou uma interface administrativa de ativação.
Manter a identidade suspensa e o vínculo convidado até concluir essas etapas.

Antes do commit, uma falha reverte tudo. Após o commit, não apagar identidades ou
vínculos automaticamente: a trilha permite distinguir objetos criados de objetos
preexistentes, mas eles podem ter recebido novos vínculos. Manter as contas
bloqueadas e preparar uma migration compensatória revisada ou restaurar o snapshot
conforme o plano do ambiente. Não editar migrations aplicadas nem usar `repair`
para esconder divergências. A remoção futura de `app_users` é uma etapa separada.

## Validação e critérios de aceite

- [x] Autenticação com a identidade global real e principal sem senha.
- [x] Seleção de oficina retorna 401/403 e não aceita identidade do cliente.
- [x] Vínculo ativo executa; suspenso, inexistente e de outro usuário não executam.
- [x] JPA/JDBC compartilham transação com tenant autorizado.
- [x] RLS bloqueia leitura e escrita cruzadas; runtime mantém SELECT nas tabelas atuais.
- [x] Commit, rollback, erro SQL, exceção Java, Error, conexão reutilizada e
  transação externa restauram ou limpam os contextos corretamente.
- [x] Fixtures só operam em `fixflow_test` e são removidas após falhas.
- [x] V8/V9 e privilégios do runtime são conferidos nos dois bancos locais.
- [x] Backfill preserva legado, impede ativação automática, trata conflitos e é idempotente.

Os testes de escrita usam uma cópia descartável de `app_users` e sua policy real,
concedendo CRUD apenas à cópia no banco de testes. O runtime continua sem escrita
nas tabelas atuais da aplicação.

```bash
./mvnw clean verify
```
